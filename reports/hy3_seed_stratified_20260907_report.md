## 6. 典型案例

### 案例 A：`lis_length`，高难题正确完成

Hy3 正确区分子序列与子数组，并选择 `tails + lower_bound`：对每个值替换第一个大于等于它的位置，使相等元素不能扩展严格递增长度。过程给出最小结尾不变量、`O(n log n)` 时间复杂度和空数组、重复值、下降序列边界。

结果：6/6固定测试通过，60次属性测试通过，5/5专业评审给出明确结论。人工复核确认最终答案与过程均成立。该样本说明模型能处理受复杂度约束的非平凡算法与证明。

运行中该题的评审服务曾两次暂时不可用。断点机制保留已生成答案，第3次尝试只重跑评估并成功完成，因此服务波动没有被计为模型错误。

### 案例 B：`coin_change`，思路正确但实现失败

Hy3 给出的完全背包状态、转移、不可达哨兵和复杂度分析均成立，也明确说明一般币制不能使用贪心。但生成代码最后一行写成：

```python
return -1 if dp[amount] > amount else dp[amount)
```

右括号与方括号不匹配，代码无法解析，所有测试在加载前终止。评估器将首错定位到第6步实现环节，人工复核给出相同结论。

该案例说明过程评估不能只检查算法文字；代码语法和执行证据能够识别“推理正确、实现未兑现”的失败。它也是本轮唯一确认的真实模型错误。

### 案例 C：`grid_shortest_path`，执行策略造成误报

Hy3 使用四方向 BFS，正确处理起终点障碍、`1x1` 网格、访问标记和不可达情况。实现使用标准写法：

```python
from collections import deque
```

当时的沙盒禁止任何 `import`，虽然运行环境已预注入受限的 `collections` 门面；生成提示却没有告诉模型必须直接使用该门面。自动评估因此返回 `SecurityPolicyError: ImportNotAllowed`，并把第6步标为实现错误。

人工复核认为该代码在题面和已公开执行契约下正确，因此这是评估器误报。当前实现已让生成提示直接复用沙盒的安全导入契约，并允许 `collections.deque` 等经过严格白名单验证的标准库成员；其他模块、星号导入、相对导入和直接 `__import__` 仍被拒绝。该案例显示确定性执行证据也必须建立在公开、一致的契约上。

为排除目视判断偏差，复核时在标准 Python 环境重新执行原始候选代码：6/6固定测试全部通过，并使用同一题目的 Hypothesis 输入策略搜索200个用例，未发现与参考实现不同的反例。修复后还在当前沙盒运行器的本地后端重放同一候选代码：6/6固定测试通过，默认预算60次属性测试通过且未发现反例。Docker CLI 在本机不可用，因此本轮没有把该结论扩展为 Docker 端到端验收。该补充验证只支持“当前样本应判正确”，不构成对所有可能输入的形式化证明。

### 案例 D：结构化输出与服务重试

`coin_change` 第一次生成返回了无法解析的结构化 JSON，自动重试后得到可评估答案；`lis_length` 的评审服务两次暂时不可用，续跑时复用已有答案。最终6条全部完成且没有重复生成已完成题目。

这些重试属于运行可靠性信息，不计入模型正确率。当前报告只保留最终成功调用的完整元数据，因此不能用它精确核算所有失败调用消耗。

## 7. 能力边界判断

人工复核后的点估计在 easy 和 medium 均为100%，hard 为50%，表现下降信号出现在 hard。由于每层只有2题，easy/medium 的95%区间为34.24%-100%，hard 为9.45%-90.55%，区间高度重叠。

本轮结论是“hard 层出现待验证的下降信号”，尚不能确认能力临界点。要形成可提交的边界结论，需要在相同量表下扩大每层样本、固定抽样，并重复生成以估计温度和模型随机性带来的波动。
